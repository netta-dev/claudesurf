# Architecture

README.md documents what the agent and the human see: the read format with its overlay blocks, an acting call's head lines and `Changed:` hunks, settling, the allowlist and its `Blocked:` lines, the `console`, `network`, and `fetch` formats, the challenge signals, the handoff's notifications and taskbar marks, the action log, and the tab list. This file covers the code behind them and points to README.md for each format. Each module's header comment holds its own rules.

## Modules

- **`server/server.js`** — the MCP stdio bridge, one per Claude Code session. It builds the tool definitions once at start, validates calls with `dispatch.js`, POSTs `{sessionId, tool, action, args, env}` to the daemon over the `0600` Unix socket, renders the envelope with page text inside the nonce delimiter, and maps its own failures onto outcomes (unreachable daemon → `setup_error`, request timeout → `error`). `sessionId` comes from `CLAUDE_CODE_SESSION_ID`, so a respawned bridge reuses its window.
- **`server/daemon.js`** — one per OS user: the HTTP server on the socket, the handler table, and `ensureBrowser`, which launches once for a burst of first calls, retains the last request's graphical environment, and attaches the registry and then the gate to each launch's connection before `enableTargets`. It constructs `Policy`, `Gate`, `ActionLog`, `Notifier`, and `Handoff` at start, answers `policy` itself, and sends the restart announcement when `reapOrphan` found a browser record.
- **`server/dispatch.js`, `envelope.js`, `diagnostics.js`, `paths.js`, `keys.js`, `policy.js`** — loaded by both processes: the action table, its validation, and the tool definitions; the outcome vocabulary; the leveled stderr logger; the paths with their overrides, and the graphical variables the bridge forwards with the `XAUTHORITY` check that the browser's and the desktop tools' environments share; `press`'s key grammar; and the host and http(s) checks. `Policy`, the allowlist store, is the daemon's alone.
- **`server/cdp.js`** — the protocol client over the pipe's fds 3 and 4: id correlation, `sessionId` routing, event fan-out, timeouts and deadlines, and EOF and a pipe error both treated as a close. **`server/browser.js`** — binary lookup, launch and handshake, the browser record, the orphan reap, and `enableTargets` (auto-attach and download denial).
- **`server/sessions.js`** — `Session` records and the target registry (`targetRecord` lists a target's fields), with attribution by opener, the role claim, window creation and repair, the working tab's arming, and the window-state drop. **`server/tab-records.js`** — tab numbers, the earlier-working stack, `switchWorking`, and each tab's kind. **`server/requests.js`** — each target's in-flight requests, and the stages of each that it hands to network capture's sink. **`server/retained.js`** — each tab's retained render.
- **`server/gate.js`** — the domain gate's three checks. **`server/arming.js`** — the commands that put a tab under the gate and take it back out, and the rule for a tab whose arming failed. **`server/refusals.js`** — each session's refusals not yet reported. **`server/action-log.js`** — the JSONL log of every call that reaches the daemon.
- **`server/read.js`** — `page`'s assembly, paging, and `since`, plus `info` and `screenshot`. **`server/region.js`** — the render pipeline that a read, a `since` read, and a change summary share, from the tree pull to the retained render's replacement. **`server/overlays.js`** — the overlay blocks' renders. **`server/changes.js`** — the change summary and `since`, over **`server/diff.js`**, a pure line diff.
- **`server/input.js`** — `click`, `scroll`, `type`, `press`, and `select`. **`server/focus.js`** — `press`'s read of the focused element, before and after its keys, and the `Keys to:` and `Focus now:` lines that name it. **`server/navigation.js`** — `navigate` and `history`, and the gate's pre-check that they, `tabs new`, and `fetch` share. **`server/tabs.js`** — the four `tabs` ops. **`server/act-result.js`** — `beforeAction` and `finishAction`, the result step every acting call ends with. **`server/navigation-wait.js`** — the wait for a navigation an acting call started, the `Navigated:` verdict, and whether the gate refused the call's navigation. **`server/settle.js`** — the settle loop. **`server/refs.js`** — a ref's resolution under the staleness rules. **`server/frames.js`** — the main-frame test and whether a frame is still there. **`server/respond.js`** — the envelope a handler's result or failure becomes. **`server/action-support.js`** — what the handlers share, the sanitizers for page text and the page-script sources among it.
- **`server/challenge.js`** — detection: the vendor rows, the widget checks and their wait, and the page scan's verdict. **`server/handoff.js`** — each session's open handoff, the notification limit, the refusal notices, and the urgency hint's lifetime. **`server/notify.js`** — `notify-send`, `xdotool`, and `wmctrl`, with the environment they run under and their failure logging.
- **`server/ring.js`** — a capped list of entries numbered from one daemon-wide counter, read after a cursor. **`server/console-capture.js`** — `Console` and `Log` capture and the `console` read. **`server/network.js`** — the request records built from `requests.js`'s stages, the main-frame documents' challenge headers, and the `network` read with its bodies. **`server/fetch.js`** — the `fetch` action. **`server/mime.js`** — the rule for a textual MIME type, shared by `network.js` and `page/fetch.js`.
- **`server/snapshot.js`** — one `Accessibility.getFullAXTree` answer read as controls, landmarks, named groups, iframe nodes, overlays, up to 500 options per combobox or listbox, and a scope root, plus the omission report and the overlay pick; pure over protocol data. **`server/render.js`** — the daemon side of one unit's render, and the pieces a read assembles: inlined frames, `find`, the links index, the header lines, the overlay markers, and the paging cut.
- **`server/page/*.js`** — page-side scripts that run in the browser and are sent as source; never `require`d. `action-support.js` splices `state.js`, the one definition of hidden, disabled, and masked, into `render.js`, `walk.js`, `click.js`, `edit.js`, `select.js`, `detect.js`, and `visible.js` at their `// @include state.js` line, and `focused.js` into `edit.js`, `collapse.js` into `render.js`, `walk.js`, `edit.js`, and `select.js`, and `nearest.js`, the response fields nearest a widget's `<iframe>` or `<frame>`, into `detect.js` and `visible.js` the same way; `focus.js` embeds `focused.js` in `press`'s focus read. `render.js` runs after the three libraries, which `action-support.js` reads from `node_modules` and concatenates with it. `detect.js` is detection's page scan, `visible.js` its check of a widget's `<iframe>`, and `fetch.js` the `fetch` action's request, which takes `mime.js`'s pattern source as an argument.
- **`server/static/session.html`** — the session page both tabs start on, addressed by `file://`: role, session id, and start time in the URL fragment; `render(name, description)` for the label; and two `target=_blank` links to itself that the daemon clicks to open the other role's tab.

## Request flow

`validate` → `ensureBrowser` → `sessions.ensureWithNotes(sessionId)`, serialized per session, whose `repair` gives the session a working tab (Session windows) → the handler in the session's queue slot, which first closes the session's handoff → the envelope, which `respond.js` builds in that same slot, and, when it is `needs_human`, a fresh handoff (The handoff) → the action-log record → the response. Building the envelope inside the slot keeps it from taking a refusal or a note that a later call led to. The slot clears the call's marks in a `finally` as the handler ends.

`policy` skips `ensureBrowser` and `ensureWithNotes`, so it neither launches Chrome nor opens or repairs a window, and still runs in the session's slot, where its response takes the pending refusals; its slot leaves an open handoff open. A `validate` failure returns its `schema_error` directly, and a failure of `ensureBrowser` or `ensureWithNotes` maps through `failureEnvelope` outside any slot; either leaves the session's refusals, notes, and handoff in place.

The bridge times out at 35 s; the daemon runs every request under a 33 s deadline:

- a launch gets 15 s, and window creation 5 s;
- `navigate` waits up to 25 s, cut to 2 s before the deadline, for a new document that has fired its own `DOMContentLoaded`, then settles;
- an acting call waits up to 10 s, cut the same way, for a navigation it started, then settles for up to 5 s, cut so that 3 s of the deadline remain for the change summary;
- an acting call's detection, and its wait of up to 10 s once per document for a challenge that may clear itself, keep the same 3 s reserve;
- `tabs new` waits up to 5 s for its tab and gives its navigation what is left of 25 s, or an acting call's 10 s for Chrome's error page when the navigation command answers an error;
- a fresh read settles for up to 2 s before it renders, and detects under a deadline 2 s short of the request's;
- detection's widget wait takes up to 3 s, once per document, and ends 500 ms before detection's deadline;
- `fetch` gets up to 20 s, cut to 2 s before the deadline once its world resolves, and fails before sending with under 500 ms; a `network` read's bodies share what is left, less 1 s.

## Responses

A handler returns `{ head, body?, images?, outcome?, blocked?, challenge? }`. `respond` puts the head, the dismissed-dialog lines, and the `Blocked:` and `Blocked by the page:` lines ahead of the body, so a cut can't push them out. A non-empty `blocked` makes the outcome `needs_confirmation`, with the before-acting message when every entry is a pre-check (`how: 'not started'`) and the after-acting one otherwise. Otherwise a `challenge`, which `readPage` and `finishAction` set (Detection), makes it `needs_human`, whose message names the challenge's type and the session's label and keeps the page's text out; otherwise the outcome is the handler's, `unsettled` or `success`. `needs_confirmation` outranks `needs_human`: a navigation that the gate stopped left the tab on its old page, so the challenge would be the old page's, and the host to ask about comes first. The notes are `ensureWithNotes`'s, then those the session took during the slot, then one per dismissed dialog.

`failureEnvelope` maps a thrown error onto an outcome. Inside the slot it carries the pending `Blocked by the page:` lines as its payload with the session's notes, and returns the working tab's URL for the log. Outside it, it takes neither, and `daemon.js` reads the URL with `respond.js`'s `workingUrl` instead, on the session that `Sessions.peek` returns, so an unknown session id doesn't create a session.

## Reading a page

`read.js` settles, then `region.js` renders the region as a pipeline over units, and `read.js` assembles the payload around it (README.md, What a `page` read returns). A unit is one document the daemon can pull a tree from and run script in: the page's main frame, a same-process child frame (the page target plus a `frameId`), or an out-of-process child frame (its own iframe target). Per unit: one `Accessibility.getFullAXTree`; one `DOM.resolveNode` per control, landmark, group, iframe, overlay, and scope root, under an object group released in a `finally`; one `DOM.describeNode` per iframe node for the frame it holds; and one `Runtime.callFunctionOn` on `claudesurfRender` in the unit's isolated world.

The page script builds an annotated clone of the unit's document, hands it to Readability when the chain asks for it, and runs Turndown over it. Markers key on a `data-cs-ref` stamp that the clone walk puts on the described nodes after it strips the page's own, their fields and URLs are escaped, and page text loses the two characters the renderer reserves (the frame placeholder's NUL and the private-use filler that pads a blank control), so page text can't close a marker, pose as one, or forge a placeholder. `page/render.js` holds the rules.

`region.js` then reads the frames inside what rendered, one level at a time within README.md's frame limits, each unit under its own 5 s budget. The first level's parents are each overlay block's render and then the region's, so a dialog's frame takes a unit ahead of the page's own. Each frame's output replaces the `\u0000frame:<ref>\u0000` placeholder its parent left, capped at 8,000 characters per frame and 16,000 per read, the blocks' frames drawing on that budget first. A frame that lacks a placeholder of its own in what its parent rendered isn't read. The omission line names it only when the page unit's own tree holds its `<iframe>`, so a frame nested in a rendered frame, or in the frame that a frame-scoped read covers, can go unnamed, and an out-of-process one does.

A frame's failure degrades to a `(not readable)` line, and a frame whose own document changed during its render counts as failed; a same-process frame's own navigation doesn't move a generation the caller can check, so `render.js` takes every resolved node coming back null as that signal. The region's own unit fails the read with a `RenderError` carrying what the render threw; that text goes to the journal, since a page can shape it. A generation that moved after the region's render, the hidden walk's stashed array gone, or, under `since` or `summary`, a generation that moved during the page's tree pull or the `main` scope's root lost before the render is a `DocumentChangedError`; a plain read whose ref scope a commit overtook during the pull answers `stale_ref` first. The hidden-control count and the `hidden=true` list come from `walk.js` over the page target's whole document.

## Overlays

`region.js`'s `pick` chooses the overlays a read renders as blocks, through `snapshot.js`'s `blockOverlays(snapshot, rootNodeId, chain)`, before the page render. For a scope in the page, it passes the scope root and the chain the scope resolved to before the render's fallback. For a read scoped into a frame, it passes the chain `all`, which picks dialogs alone, and as the root the page's `<iframe>` that leads to the frame. README.md's Overlays paragraph gives the rules each chain applies.

When the region is the page unit's, its render gives each picked overlay an `overlay` descriptor whatever the scope root, so the region leaves it out. `overlays.js` then renders each picked overlay in the page unit as a ref scope renders its root, one `renderUnit` call at a time, before the frame levels, dialogs first, within the limits README.md gives; a skipped overlay spends a call but not a block. A block's failure marks it unreadable, except a `TargetGoneError`, which fails the read. The omission report counts each block's remaining refs as rendered and its hidden refs as hidden.

## Targets and attach

`Target.setAutoAttach` runs with `flatten` and `waitForDebuggerOnStart` for `page` and `iframe` targets, at browser level for pages and again on every page and iframe attach, the per-target call that surfaces out-of-process child frames. Both calls let worker targets through as well: the pause holds a new dedicated, shared, or service worker whatever the filter says, and reports it only when the filter lets it through, so a worker left out never runs (Cloudflare's Turnstile never finished, and its sign-in button stayed disabled). `onAttached` releases each worker and detaches from it, without recording it. An iframe target is recorded like a page, but without the window lookup, with `type: 'iframe'`, the parent target whose protocol session carried its attach, and a frame number from its root page's counter that is never reused.

The attach handler (`onAttached`, `queueAttach`) takes a page target through these steps:

1. When the tab's opener's root page is in a session, it attributes the tab to that session (role `opened`, `openerPage`, a tab number), since the tab's first request can be refused, and the tab closed, before any command answers.
2. It queues the commands: arming's for an attributed tab, then `Browser.getWindowForTarget`, `Page.enable`, the per-target auto-attach, and `Emulation.setFocusEmulationEnabled`. Chrome runs a protocol session's commands in order, so a queued `Fetch.enable` gates the first request.
3. It wakes the opener's waiters and sends `Runtime.runIfWaitingForDebugger`, which goes out even when a step before it throws.
4. Only then does it await anything, since awaiting first deadlocks a paused tab (Non-obvious gotchas). Every queued command's promise has a handler before the first await, since a wedged renderer fails several and an unhandled rejection would end the daemon.
5. On `Page.enable`'s answer it reads `Page.getFrameTree` for a tab attributed by opener and for a page attached without a URL, recording the URL, the main frame's id, and `committedWeb`. Once the window lookup, the auto-attach, and focus emulation have settled too, it claims the tab, unless `Page.enable` or the frame-tree read failed; arming's outcomes don't gate the claim. `arming.onRejections` runs after the claim.

The target's `ready` resolves, with arming's outcomes or null, once `Page.enable` and the arming commands have settled, and with null when the target goes first.

A target whose URL is the session page with `#role=<identity|working>&session=<id>` is claimed for that role, at attach or on a main-frame `Page.frameNavigated` while it lacks a role or is a page-opened tab. A second tab of a role is let go, and a tab that another session held is let go from that session before the claim. Any other tab stays unowned.

## The domain gate

A tab is gated while it belongs to a session and isn't its identity tab: the working tab, the earlier working tabs, and each tab that one of the session's tabs opened. `Gate.attach` takes `Fetch.requestPaused` on each launch's connection and sets the gate as the registry's `interceptor`, without which arming leaves out `Fetch.enable`, as in the live tests that drive `Sessions` alone.

`armed` goes up once every arming command but the prerendering switch has succeeded, and an arming epoch keeps a late outcome from raising it again. A tab is armed at attach when its opener's root page is in a session, which covers the identity tab, armed although the gate passes its requests. `repair` arms the working tab when it isn't armed, which covers the tab `Target.createTarget` opens, since that tab lacks an opener, and fails the call with `error` when that arming fails, leaving `armed` down for the next call. A tab that leaves its session through `letGo`, which the window-state drop and `claim` call, is disarmed, unawaited. For a tab armed at attach whose arming failed, `arming.onRejections` closes an `opened` tab with a session note, unless the only failures were timeouts of `Network.enable` or the bypass, after which its requests still pause at the gate; it leaves a claimed working tab for the next `repair`, and any other tab unarmed.

The request handler continues a request of a tab outside the gate, one that isn't `http` or `https`, and one whose `frameId` isn't the target's main frame (`frames.js`), since frame documents are outside the gate. It checks every other request, each redirect hop included, with `Policy.allows`, which covers the allowlist file and the session's `allow_once` grants. A refusal goes through `gate.refuse`, which records it on the session and notifies the refused tab's waiters, and then `Fetch.failRequest` with `Aborted`; a tab that counts as new (`isNew`: opened by a page, never the working tab, and yet to commit a web page) is closed. A refused request of a tab whose `closing` is set skips `gate.refuse` and fails with `Aborted` alone, so it isn't recorded and doesn't close the tab again. A refusal leaves the tab's navigation counters alone, since a same-origin `<a download>` link's request pauses here too (Non-obvious gotchas); a refused navigation ends when Chrome fails its document request (Acting calls). A throw while judging fails a gated tab's request and continues any other's, so every pause gets an answer.

`navigate`, `history`, `tabs new`, and `fetch` (under the kind `fetch`) pre-check their own URL with `Gate.check`, which returns an entry with `how: 'not started'` without recording it; the handler returns it as `blocked` beside the working tab's state lines, without acting. The backstop, `Gate.onCommitted`, runs from `onFrameNavigated` for a gated page target's main-frame commit, before the registry records `committedWeb`. An `http` or `https` commit to a host the allowlist doesn't cover, which a back-forward cache restore or a prefetched activation makes without a request Fetch sees, closes a new tab and sends any other to `about:blank`, recorded with the kind `restore`.

`refusals.js` keeps each session's refusals not yet reported, at most 20, a repeat merged into its entry's count. `refusals.record` reads the call's marks (Acting calls), outside the queue, to choose the entry a full list drops, and `finishAction` takes the call's own entries (`isOwn`) when settling ends and returns them as `blocked`. Every other entry stays for the next response built in a queue slot.

## Acting calls

Every handler that acts — `click`, `type`, `press`, `select`, `scroll`, `navigate`, `history`, and `tabs new` — calls `beforeAction` before it acts and `finishAction` after. `beforeAction` records the tab's navigation, download, same-document, and generation counters and the requests' mark, and sets the call's marks on the session, `{ seq, nextTab, workingTargetId, newTab }`. `acting` runs the command that acts and answers `error` saying the action may have run when that command times out, since a timeout doesn't cancel a command in the browser; `tabs new` handles its own commands' timeouts.

`finishAction` waits for a navigation the action started, settles, and builds the head (README.md, What an acting call returns). A navigation counts as started when `Page.frameStartedNavigating` with a cross-document `navigationType` moved the tab's counter at any point before settling ends: settling stops, and the wait runs again. The wait (`waitForDocument`, event-driven through `Sessions.waitUntil`) ends once the tab's current document is newer than the wait's start and has fired its own `Page.domContentEventFired`, or once the tab's latest navigation, started since the wait's start, has ended without a commit (`navigationsStopped`, which `onRequestFailed` sets when Chrome fails the navigation's document request): Chrome dropped it, as it does a navigation that the gate refused or one that turned into a download, which Chrome denies. `Page.downloadWillBegin` doesn't stop a navigation: Chrome sends it after it has failed a download navigation's document request, and also for an `<a download>` link or a blob URL, which don't start a navigation, so it can arrive while the page's own navigation is under way. Each wait starts from the tab's state as the one before it ended. `Navigated:` is judged once, from the tab's record as the head is built, by three things: the generation against the call's starting counters, which are `beforeAction`'s, or, when `tabs new` reports on its new tab, that tab's from before it navigates; `loadedGeneration`, the generation whose own `DOMContentLoaded` fired, which a back-forward cache restore sets with its commit; and whether a navigation started after both the call's start and the current document's commit (`navigationsAtCommit`) without a drop since (`navigationsStopped`), which a refusal leads to. The change summary runs when the call ended on the tab and the document of those starting counters, so a `tabs new` whose navigation Chrome dropped, which leaves the new tab on its blank first page, prints `Changed: not tracked (read the page first)`.

Once the action has acted, a failed step prints in the head instead of failing the call, unless the pipe closed. After a failed step `finishAction` checks whether the working tab is still registered, since a command in flight as a tab closes gets a protocol error or a timeout as often as a `TargetGoneError`; when the tab is gone, the head is the `Tab:` line with the `Opened:` lines, and the next call's `repair` finds a working tab. Each tab attributed during the call, numbered at or above the marks' next number, gets an `Opened:` line unless it has left the session, is the working tab or the identity tab, or has `closing` set.

`fetch` sits on `claudesurf_act` but only reads: it calls neither `beforeAction` nor `finishAction`, so it doesn't settle, diff, or detect. It takes the URL's absolute form, `new URL(url).href`, for the gate, the script, and its lines, since the page's fetch resolves a form such as `http:host/path` against the document's base URL, which `<base href>` sets, and would reach another host than the gate read; `navigate` and `tabs new` pass the URL to `Page.navigate`, which parses it without a base, as the gate does. `dispatch.js` refuses a URL that carries a user name or password, which the page's fetch throws on. After the pre-check it calls `page/fetch.js` once in the working tab's main-frame isolated world through `sessions.world` and `sessions.callFunction` rather than `callInWorld`, whose retry on a missing context would send the request again from another document. A commit while the world resolves can leave it the new document's, so `fetch` compares the tab's generation once the world resolves and answers `error` before sending when it moved; a commit during the fetch, including one that lands before a successful answer is read, answers `error` saying the request may have been sent.

## Settling

`settle.js` combines three signals, by the definition in README.md's Settling paragraph:

- `requests.js` counts a target's document, script, stylesheet, XHR, and fetch requests from `Network.requestWillBeSent` to `loadingFinished` or `loadingFailed`, on each tab where arming enabled `Network`. A request counts past 5 s in flight only when the acting call started it, which it did when its first `requestWillBeSent` came after `beforeAction`'s mark; a redirect hop keeps that verdict and restarts the 5 s clock. A main-frame commit ends the old document's requests, and an out-of-process frame's document request ends when the frame's target attaches, since Chrome reports its end there.
- `page/settle.js` installs a `MutationObserver` over `childList` and `characterData` of the document and every open shadow root, in the main frame's isolated world, on its first call; it lasts as long as the world, which is one document.
- An input action into a child frame (an `f`-ref, a bare ref read in a same-process frame, or, for `press`, an `<iframe>` or `<frame>` holding focus) runs the observer in that frame's world too. When the frame's probe fails, `frameThere` decides, and a frame that went drops its signal.

The loop re-checks every 100 ms and on each counted event, and each probe's deadline is the end of the settle budget, with a 50 ms floor. `CLAUDESURF_SETTLE_QUIET_MS` shortens the 500 ms quiet window for tests; `settle.js` reads it on each call.

## Change summary and retained renders

`retained.js` keeps one render per tab on the session, uncut and before `find`, with its parameters (`scope`, `article`, `links`, `hidden`), its source (`read`, `since`, or `summary`), the time the render began, and the generation. `renderRegion` replaces it on every render; a render over 500,000 characters, counting its region, its hidden section, its overlay blocks, and each link's ref and URL in its link lists, leaves a size marker instead. An entry counts only at its generation and goes with its target and with the window state. A read with `offset` above 0 and matching parameters slices it without settling or rendering (README.md, `offset`).

`changes.js`'s `renderChanges` serves the change summary and `since` alike. It answers untracked without rendering when the tab lacks a retained render of this document, when it holds the size marker, or, for a summary, when the tab isn't the target the session's last read covered. Otherwise it renders the tab again through `renderRegion` with the retained parameters, a scope ref resolving with `ownRender`, and diffs the two renders' non-blank lines, the overlay blocks apart from the region. `diff.js` runs Myers's O(ND) diff between the common prefix and suffix and gives up past 1,000 edits, since the diff runs on the event loop that answers every paused request. A lost scope ref answers untracked and drops the retained render. A summary's other failures print in the head and leave the call's outcome alone, except a closed pipe or a working tab no longer registered; a `since` read's propagate to `read.js`. The new render becomes the retained render and refreshes the ref set.

## Detection

`challenge.detect` judges the working tab after a read that renders, whole or `since`, in `read.js`'s `stateAfter`, and in `finishAction`'s wait and settle loop once settling ends; a paging read and every handler that doesn't act skip it. README.md (Challenges and the handoff) gives the signals and their order. It reads three sources and stops at the first match; the widget check and the page scan run together, so a widget match costs the scan too:

1. **Headers.** `network.documentSignal(t)` looks up the challenge header values of the response whose loader id equals `t.loaderId`. The registry records `t.loaderId` from the main frame's `Page.frameNavigated`, or from the attach's `Page.getFrameTree` read for a first commit that arrives without that event. `network.js` keeps the last 10 main-frame `Document` responses per tab by loader id, so a back-forward cache restore, which commits under its document's old loader id, finds that document's response while the tab still holds it.
2. **Widgets.** A widget is a frame that a `VENDORS` row names by its URL: a frame target, or an `<iframe>` or `<frame>` that the page scan lists. A frame in the page's own process doesn't get a target, so a widget served from the page's own site, such as reCAPTCHA on Google's pages, reaches detection through the scan alone. For each frame target under the tab whose URL a row names, `checkWidget` asks the parent target for the `<iframe>` with `DOM.getFrameOwner`, resolves it into the parent's main-frame isolated world under the object group `claudesurf-detect`, and runs `page/visible.js` on it. That script applies `state.js`'s hidden rule and the 20 × 20 minimum and reports the state of the response fields nearest the `<iframe>`, `filled`, `empty`, or `absent`; `page/nearest.js` holds the walk that finds them, which the page scan shares. A frame's style stops at its own document, so for a widget frame nested under another frame target, `checkWidget` runs the same script on each `<iframe>` between it and the page, and the widget counts only while each of them does. An `<iframe>` that the world can't resolve, such as one inside a same-process child frame, doesn't count through its frame target, though the scan finds it when that child frame is a same-origin one that it walks; `DOM.getBoxModel` can't stand in, since it misses `visibility: hidden`, which standby widget frames use. A row without a response field counts once per document: `detect` answers `once` for it, and `keep` records the generation in `widgetReported` when the caller keeps the result. `finishAction` prints the challenge of a call with refusals of its own without keeping it, since that call answers `needs_confirmation` and doesn't open a handoff.
3. **Page scan.** `page/detect.js` runs in the main frame's isolated world with each widget check, over the document, its open shadow roots, and the documents of its same-origin child frames whose `<iframe>` or `<frame>` counts as a field does, and reports the title, a password field, the two-factor form that matched, `#px-captcha`, and each visible `<iframe>` or `<frame>` of at least 20 × 20 with an http(s) `src`, with the state of the response fields nearest it under each row's selector. Its header comment holds the field rules. The scan's title serves every match but a header's; after a header match the scan is skipped and `pageState` reads the title, and a failure of that read leaves the title empty, which skips the urgency hint.

Two waits are each spent once per document, by the generation they ran on, and only by a call with at least 500 ms left for the wait; a call with less leaves it to a later call. `detect`'s widget wait (`widgetWaited`) checks the widgets again every 500 ms, for up to 3 s, until each unsolved one with a response field has it filled or a navigation starts, and checks once more after a navigation ends it. It stops 500 ms before detection's deadline, so the last check, whose scan reads the title, has time to answer. `finishAction`'s wait for a match with `clears` (`clearWaited`) runs `Sessions.waitUntil` for up to 10 s until a navigation starts. A navigation that starts during detection or a wait sends the loop round again, as one that starts during settling does.

`detect` resolves `{ challenge, generation, once }`, the generation as detection began, and a commit before it ends makes `challenge` null. `finishAction` keeps the challenge only when the tab's generation as it reads the state lines equals detection's, and `read.js` once `stateAfter`'s `requireSameDocuments` has passed on the render's documents, the tab's among them, and the payload is built, so a `needs_human` outcome and its `Challenge:` line describe the document that the state lines print, and a read that fails spends nothing. `detectOrLog` logs a failed detection at info and answers null, except for a closed pipe and a working tab gone from the registry, which take the caller's own paths.

## The handoff

`daemon.js`'s `slot` calls `handoff.closed(session.id)` as each queue slot starts, except `policy`'s, and `handoff.opened(session, result.challenge, url)` at the slot's end when `respond` built a `needs_human` envelope. A session's queue runs one slot at a time, so its handoffs open and close in the order of its calls. Neither call waits on the desktop tools.

`Handoff` keeps the open handoff `{ windowId }` per session, the hosts and times of the refusal notices per session, and the time of each notification by session, type, and the URL's origin and path, pruned past 10 minutes. `opened` notifies unless the same session, type, and origin and path notified within 10 minutes, then finds the window through `Notifier.findWindow` (`xdotool search --pid` on the browser's pid, then each window's name against `<title> - `) and marks it only when the same handoff is still open, so a `closed` that ran first leaves the window unmarked. A window's mark commands run one after another, so a clear lands after a set that began before it.

`Gate.refuse` calls `gate.onRefusal` from a microtask and logs its throw at warn, so the callback runs after the gate has answered the paused request or acted on the commit and can't keep the gate from acting; `daemon.js` points the callback at `handoff.refused`. The request handler's and the backstop's refusals reach it; the pre-check's, which `Gate.check` returns unrecorded, don't.

`Notifier` runs each tool with `execFile` under a 5 s kill and never rejects. The tools run under the daemon's environment plus the last request's value of each graphical variable that the daemon lacks, so `notify-send` keeps the daemon's session bus while `xdotool` takes the bridge's `DISPLAY`; the browser's launch takes one environment or the other whole. The restart announcement goes out before any request, so it runs under the daemon's own environment. A missing binary logs once at info, and a failed run logs its first stderr line at info the first time that line appears and at debug after. Mutter and Muffin (Cinnamon) refuse demands-attention to a window in plain view while `wmctrl` still exits 0, so on them a visible session window carries the urgency bit alone; the headful case asserts both marks only on a minimized window.

## Capture

Each armed tab keeps two lists, each a `Ring` of 500 from `ring.js`: `console-capture.js` fills one from `Console.messageAdded` and `Log.entryAdded`, and `network.js` fills the other with the records that `requests.js` hands it as each request ends. `arming.arm` sends `Console.enable` and `Log.enable` beside its own commands, unawaited and each with a rejection handler, and keeps them out of arming's outcomes, so they can't close a tab or fail a call. `arming.disarm` sends both disables and drops both lists, and `Sessions.forget` drops them with the tab. Arming's `Network.enable` has Chrome keep up to 10 MiB of response bodies per tab and 1 MiB per response, which a filtered `network` read takes with `Network.getResponseBody`. Both modules record only on a tab whose `armingSent` holds, which arming sets as it sends and disarming clears, so an event that lands after disarming leaves nothing behind. Chrome passes a console message's text and a request's URL through uncut (Non-obvious gotchas), so a console entry keeps its text collapsed and cut to the 1,000 characters that print (`collapsedText`) and its URL's first 1,000, and a request record its URL's first 2,000.

**Network records.** `requests.js` owns the request lifecycle that settling tracks, and capture records that lifecycle rather than a copy of it. `Sessions.attach` passes `network.js`'s `sink`, `{ started, response, ended }`, to `attachRequests`, which holds the sink and the registry's logger module-wide and replaces both at each call, since `commit` and `endFrame`, which the registry calls itself, end entries outside `attachRequests`. `started` builds the record from `requestWillBeSent` without its headers or post data, and the tracker's entry carries it unread. `response` takes `responseReceived`, which the tracker subscribes to for capture alone, adds the status and the MIME type, and for a main-frame `Document` keeps the two challenge header values by loader id. `ended` records how the request ended and numbers the record into the ring. The endings are `finished`, `failed`, `redirect` for a hop that a later `requestWillBeSent` under the same id replaces, `ended by a navigation` at a main-frame commit, and `continued in a cross-site frame` when its frame attaches as its own target. An entry that the tracker evicts past its 1,000 in flight, or drops with its tab, ends unrecorded. The tracker calls the sink after its own bookkeeping, under a try/catch that logs a throw at warn, so a sink that throws can't skip settling's counts. `requests.js` doesn't require `network.js`, and `network.js` requires `requests.js` for `inFlight` alone.

**Cursors.** `ring.js`'s daemon-wide counter numbers a console entry as it arrives and a request record as it ends, so a read that carries an earlier read's cursor sees how each request in flight at that read ended. Each ring keeps the highest number it dropped, for `Missed:`, and a cursor above `issued()` comes from before a restart, so the read lists every entry kept. An uncut answer's `Next:` is `issued()` as the read scanned its list, which moves a filtered poll past the entries the filter skipped; a cut answer's is the `after` that continues at the cut entry. `printEntries` holds the budget loop, the cut line, and that choice of `Next:` for both reads; a `network` read's filter matches the needle against a record's URL and its `safeUrl` form, since the line prints the latter. A `network` read lists `requests.inFlight`'s records after the numbered ones, in an uncut answer only, taken once the bodies are read, so a request that ended meanwhile lists in the next read rather than as in flight, and in-flight lines past the budget fold into the `… and N more in flight` line without cutting the answer, since they lack a number to continue from.

**Dependencies.** Neither capture module, nor any module that either loads, requires `sessions.js`: `sessions.js` loads `arming.js`, which loads both capture modules, before it sets its own exports, so the require would give an empty object. Both take the registry from their callers' arguments and stay off `read.js`, `respond.js`, and `refs.js`, which require it.

## Session windows

`Target.createTarget({newWindow: true, background: true})` opens the session page as the working tab. The identity tab is opened from it by Ctrl-clicking the page's identity link with real mouse events (`modifiers: 2`), which yields a background tab, so the working tab stays active. `repair` runs on every `ensure`:

- When the working tab is gone, the most recent live tab on the earlier-working stack, registered and still the session's, becomes the working tab.
- With the stack empty and the identity page intact, a scripted `userGesture` click on the identity page's working link opens a foreground tab, in whatever window the identity tab now sits in.
- With the stack empty and the identity tab gone or navigated away, the whole window is recreated under the retained label.
- An identity tab that went while the working tab stays is left absent. One that failed at window creation while the working tab came up is reopened in place from the working tab's link on the next `ensure`, or left absent when that fails again or the working tab has left the session page.

Each of these repairs leaves a note on the session, the identity tab's failed retry included. `onDestroyed` drops the window state — the window id, the tabs and their numbers, the stack, the ref sets, the last-read target, the retained renders, and the refusals unless a call is running — once the working tab is gone and none of the session's other tabs is in the session's window, judged by the `windowId` the registry last recorded, a pending or failed lookup counting as in it; the drop disowns every tab the session still holds. A session working in a popup outside its window therefore keeps working there after the human closes the window, until the popup closes. Pipe EOF drops every window and target; labels survive.

## Tabs

A session's tabs are its working tab, its identity tab, and its opened tabs: those its tabs opened and the earlier working tabs. `tab-records.js` numbers each `t<n>` from a per-session counter that never reuses a number; a tab keeps its number across roles, and a recreated window's tabs take new ones. Three things read a tab's window from the registry's `windowId` record, look it up when the record is empty, and count a tab whose lookup failed as in the session's window: the tab's kind in `tabs list`, its `Opened:` line, and `tabs new`'s choice of the tab to open from. The window-state drop runs synchronously, without the lookup (Session windows), so `tabs list` can show as a popup a tab that the drop counted as in the window.

`tabs new` opens its tab with `window.open('about:blank#<nonce>', '_blank', 'noopener')`, evaluated under `userGesture` in the isolated world of a session tab, since `Target.createTarget` can't name a window. The opener is the working tab when it is in the session's window, else the most recent live earlier working tab there, else the identity tab, wherever it is. Of the tabs attributed to the opener during the call, the call takes the one whose URL carries the nonce, answers `error` when that tab's arming failed, navigates the tab, and switches to it. When the gate refuses a redirect hop, which closes the new tab, or the new tab closes before its page loaded, the call reports on the tab it began on, which keeps or takes back the working role.

`tabs switch` changes the session's record alone, since `Target.activateTarget` would raise the window. A tab armed at attach whose `armed` is still down is first awaited through its `ready` for up to 5 s, and refused when its arming rule is closing it. `tabs close` marks the target `closing`, sends `Target.closeTarget`, which skips the page's `beforeunload` handlers, and waits up to 5 s for the target's destruction.

## Refs and worlds

A ref is `e<backendDOMNodeId>`, or `f<n>e<id>` for one read inside the iframe target numbered `n` under this page; backend ids are unique per renderer, so the prefix says which renderer's. Each session keeps a `{generation, ids}` per target, where `ids` maps each id a read found at that generation to the frame it was read in (`null` for the target's own main frame), so a node resolves in its own frame's world.

A render records each unit's refs (`recordRefs`): every control, group, landmark, iframe node, overlay node, and kept option of the unit's tree, whether or not its marker was delivered, goes into the set of the unit's target, stamped with that target's generation as it was before the unit's tree was pulled, so a read that a navigation overtook leaves nothing the new document can resolve against. A same-process frame's unit is the page target's, so its ids land in the page's set, the frames an overlay block inlines included. A read scoped into a frame also adds to the page's set, through `recordOffered`, the page's landmarks, iframes, and overlay nodes, and the controls, groups, iframes, and kept options under each rendered overlay block. `hidden=true` adds the hidden list's refs to the page's set whatever the scope.

A ref against a set of another generation returns `stale_ref`, as does an `f`-ref whose frame target is gone or has moved on; an id the set lacks, or one that no longer resolves, returns `error`. The session records the target its most recent `page` read covered (`refsTarget`; a paging read and a `since` read count, a change summary doesn't), and while it is set and differs from the working tab every ref answers `stale_ref`, since each renderer numbers its nodes from low ids; `ownRender` waives the rule for the scope ref of the tab's own retained render. A trusted click on an `f`-ref is refused; on a bare ref of a same-process frame it resolves both the element and the node its hit test found in that frame's world, the world `Runtime.callFunctionOn` compares them in.

Each step that takes remote objects from a web page holds them in an object group of its own and releases it: `claudesurf-click` for a click, `claudesurf-input` for `type`, `select`, and `press`'s focus read, `claudesurf-read-<n>` for each read unit, `claudesurf-read-overlay` for the overlay blocks, `claudesurf-read-hidden` for the hidden walk, and `claudesurf-detect` for detection's widget `<iframe>` checks. On the session page, `pageElement`, through which `ctrlClick` and `openWorkingTab` take their link, and the label's `render` take their objects outside any group and release none. `region.js` imports `refs.js` rather than `input.js`, which keeps `input.js` → `act-result.js` → `changes.js` → `region.js` from closing a cycle.

Every page-side script runs in one isolated world per target, frame, and generation (`Page.createIsolatedWorld`, world name `claudesurf`), recreated once when a command reports the context missing. The world record carries whether the renderer's libraries have been evaluated in it, so a second read of the same document doesn't evaluate them again. Main-world calls run on the session page alone: the label's `render`, `pageElement`'s lookup of a link, and the scripted click on the working link that `repair` sends.

## Dialogs and downloads

`Page.javascriptDialogOpening` is answered at once (`accept: false`, `beforeunload` accepted) and queued on the target. `respond` takes the queued dialogs of the working tab and its frame targets and prints each among the head lines; `failureEnvelope` leaves them queued, even when it carries a payload. `enableTargets` denies downloads at browser level; a navigation to a file still fires `Page.downloadWillBegin` (Acting calls). `onDownload` keeps the last 10 downloads of a tab's main frame in `downloadLog`, each `{ n, url, file }` from that event with `n` the tab's download count after it, and `finishAction` prints a `Download:` line for each one numbered above the call's starting count, three at most, then a count of the rest by the tab's download counter.

## Storage

Persistent state is the Chrome profile directory, the browser record, the allowlist, and the action log; `paths.js` gives each path and its override, and README.md gives the allowlist's format and modes, and the log's format, modes, and rotation. The browser record sits beside the socket (`<socket basename>.browser.json`, `{pid, startTime}`): written at each launch, over an earlier one, and left in place when the pipe closes and on daemon exit. Keeping it past the pipe's close leaves a record for the next start even when a restart stops Chrome along with the daemon, as systemd's default `KillMode=control-group` does. The next daemon start reaps the recorded browser if it outlived its pipe, clears the record either way, and announces the restart when it found one. `Policy` checks the allowlist with `fs.statSync` on every policy check and reads it again when its modification time or size changed. `ActionLog` appends each record synchronously. The `allow_once` grants, the log's HMAC key, the open handoffs with their notification times, and the captured console and network lists live in daemon memory.

## Non-obvious gotchas

- `Input.dispatchMouseEvent` raises the session window; so does any page-initiated target creation, a `window.open` from the isolated world included. Scripted clicks, key events, `Input.insertText`, navigation, and screenshots don't.
- Input into a tab that is not its window's active tab stalls about 5 s per event without `Emulation.setFocusEmulationEnabled`; every attached page and frame target gets it.
- `Runtime.enable` and `DOM.enable` are never sent: everything used works without them. `Runtime.enable` makes Chrome run a page's `Error.prepareStackTrace` hook whenever it reports an error, which bot-detection scripts read; `Console.enable` doesn't.
- `Console.enable` and `Log.enable` replay the document's stored messages ahead of their answers, so a tab that is armed again after a disarm records them as new entries; an enable on a domain that is already on replays nothing.
- On Chrome 157 only `Runtime` reports an uncaught exception: `Console` doesn't carry one live or in its replay, which holds only the page's `console` calls. Blink dispatches `error` and `unhandledrejection` only in the world that threw, so a listener in an isolated world doesn't see the page's exceptions.
- `Console.messageAdded` carries a message's text uncut, and `Network.requestWillBeSent` a request's URL: a 20,000,000-character `console.log` and a 3,000,000-character `data:` URL arrived whole.
- `Console.messageAdded` reports only the page's `console` calls live, and Chrome's own messages, such as failed loads and CSP violations, arrive through `Log.entryAdded` alone, so the two don't duplicate.
- `DOM.getFrameOwner` answers for an `<iframe>` inside a closed shadow root without `DOM.enable`.
- Response header names arrive in the case the server sent, so `network.js` matches them case-insensitively.
- `Network.requestWillBeSent` carries a form's `postData` whatever `Network.enable`'s `maxPostDataSize` says, so the daemon discards it.
- `Network.enable` with both buffer sizes at 0 leaves `Network.getResponseBody` answering that the content was evicted, so arming asks for 10 MiB per tab and 1 MiB per response; settling's request counts work either way.
- A fetch from a tab's isolated world is under the page's content security policy: on a page with `connect-src 'self'`, a cross-site fetch failed with a CSP violation though its server allowed the page's origin with credentials, and the same fetch from a page without the policy succeeded.
- `document.visibilityState` reports `visible` on both tabs in headful, so it can't tell the active tab; the X window title can. A screenshot of the inactive tab takes about 3 s and later ones can time out.
- Chrome exits when the pipe closes, so a daemon exit takes the browser with it; the record and reap path covers the case where it doesn't.
- On a paused new tab, `Fetch.enable` and `Page.setPrerenderingAllowed` answer while Chrome holds it, and `Network.enable`, `Network.setBypassServiceWorker`, and `Page.enable` only after the release and its first commit, which may come without a `Page.frameNavigated`. Awaiting any of the latter before the release deadlocks a noopener-opened tab, and the frame-tree read on `Page.enable`'s answer records that commit.
- `Network.setBypassServiceWorker` takes effect only while `Network` is enabled, so arming sends `Network.enable` first, and disarming sends `Fetch.disable`, the bypass and the prerendering switch set back, and only then `Network.disable`.
- `Fetch.failRequest` with `Aborted` doesn't commit an error page, so the originating document stays loaded; `BlockedByClient` commits Chrome's error page over it.
- A back-forward cache restore fires neither `DOMContentLoaded` nor `load`; its `Page.frameNavigated` has the type `BackForwardCacheRestore`, which the registry counts as a load and as a `DOMContentLoaded`.
- `window.open` evaluated in a tab's isolated world under `userGesture` opens its tab in that tab's window, the `file:` session page included; from a popup, which lacks a tab strip, it opens in whichever window was last active. With `noopener` it returns `null`, and the new target attaches with an empty URL.
- An out-of-process frame's target id equals the `frameId` its `<iframe>` element reports, and its own main frame carries a `parentId`; both are observed, not documented.
- `Page.javascriptDialogOpening` arrives on the page target's session whichever frame raised the dialog.
- `Target.targetInfoChanged` needs `Target.setDiscoverTargets`, which is not enabled; URL changes come from `Page.frameNavigated`, whose `frame.url` omits the fragment (`frame.urlFragment` carries it), and from `Page.navigatedWithinDocument`, which updates a page target's URL for its own main frame.
- `Page.frameStartedLoading` also fires for pushState; `Page.frameStartedNavigating` carries the `navigationType` that tells them apart.
- Chrome drops a navigation without a commit when the answer is a 204 or 205, when `window.stop()` cancels it, or when it hands the URL to another application, as for `mailto:`. When the page started the navigation, the `Page` domain's only sign is `Page.frameStoppedLoading`, which waits for the old document's own load to end, so it comes late, or never for a page whose load doesn't end. When `Page.navigate` started it, the command's answer carries `errorText: net::ERR_ABORTED` too. With `Network` enabled, the navigation's document request fails at once with `net::ERR_ABORTED`, its `requestId` the `loaderId` that `Page.frameStartedNavigating` carried. A download fails it the same way before `Page.downloadWillBegin` arrives, and so does a hop that the gate fails with `Aborted`. A network error fails that request too, before Chrome commits its error page under the same loader id, so only `ERR_ABORTED` marks a drop.
- A same-origin `<a download>` link's request pauses at `Fetch` as a main-frame `Document` request without a `networkId`, and doesn't start a navigation; Chrome sends `Page.downloadWillBegin` even when the gate fails that request. A cross-origin link, or a same-origin one redirected to another origin, navigates instead, and cancels a navigation already under way.
- `--no-startup-window` plus the pipe keep Chrome alive with zero windows.
- Exit code 21 before the handshake means the profile is held by another instance.
